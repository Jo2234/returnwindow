Follow one correction through three stops

Reference action: load the synthetic sample, answer delivery with 10 Oct, then change purchase from the actual OCR misread 05 Oct to ground truth 08 Oct. This sequence was exercised in the accepted production evidence; it has not been repeated for this map.

Stop 1 / input and validation

src/App.tsx — correct

Search for function correct( and function prepareCorrection(. The editable purchase field calls this handler. It delegates to applyCorrection, which validates the date and delivery ordering, creates a new case and appends the old/new values. Invalid input returns a message without changing the case.

Entry controls: ReceiptPanel passes the purchase-date target to EditableField. The handler replaces the case only after validation succeeds.

Stop 2 / results and the save schedule

src/state/case-store.ts — caseReducer / useCaseStore

Search for export function caseReducer(. It calls computeCase with the new case and supplied clock, retaining the previous result for comparison. ItemCard displays dates and differences.

The shirt moves 4→7 Nov; the mug moves 26→29 Oct. Earbuds stay 24 Oct because their answered clock is delivery-based. In the same store file, useCaseStore schedules the 300 ms save, restores on mount and cancels any queued save during reset.

Stop 3 / reload and deliberate clear

src/domain/persist.ts — saveCase / loadCase / clearCase

Search for those three exported functions and CASE_STORAGE_KEY. A strict schema validates the single case, including dates, unique item IDs and policy spans. The saved case contains extracted text/evidence, answers and corrections; receipt pixels/object URLs are not part of it. Invalid saved data is cleared.

Start over is permanent for that case: it removes the key and resets memory. A later reload must stay empty. The accepted production journey separately checked restore, clear, corrupt-save recovery and actual export-file reads.

To change this, start here

  • Field editing and validation: EditableField, prepareCorrection and applyCorrection. Keep validation failures immutable.
  • Date conventions or clause matching: src/domain/engine.ts → computeCase, src/domain/civil-date.ts and tests/unit/demo-case.test.ts. A policy-clock change needs explicit review.
  • Reload/reset behavior: useCaseStore and persist.ts; preserve the imageless save and immediate clear.
  • Calendar/evidence output: buildIcs and buildEvidenceHtml. Independent tests live in tests/unit/ics.test.ts and tests/unit/evidence.test.ts.

A practice to reuse

Write an expected result that distinguishes a plausible mistake from correct behavior. Here, changing purchase 05→08 must move the shirt and mug while leaving delivery-based earbuds unchanged. A test that only checks “three days later everywhere” would miss that distinction.

See demo-case.test.ts, journey.spec.ts and the G4 review. Likewise, the calendar tests independently require 24 Oct's reminder at 20261023T010000Z; a relative alarm on an all-day event would not guarantee Singapore time. This is a project-grounded testing practice, not a statement about anyone's learning.
