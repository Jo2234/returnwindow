## 2. Frozen MVP and explicit non-goals

**Product sentence:** *ReturnWindow tells you the last day you can return each item on a receipt, and shows the exact line of the store's own policy that says so. When the policy is ambiguous it asks you one question, and when there's no policy it refuses to guess.*

**Audience (product decision, not a personal claim):** shoppers in Singapore who buy several kinds of item in one transaction (online orders or in-store), keep e-receipts or paper receipts, and need to know, per item, whether and until when they can return it. Johan's own connection to the problem is personal and is left for him (`[JOHAN]`).

**MVP (P0, must ship):**
1. Inputs: a receipt as an image (PNG/JPG/WebP), a PDF with a text layer, or pasted/.txt text; plus the store's return policy as pasted text or a .txt file, with a short label (e.g. "Juniper Lane Goods returns page, copied 18 Oct 2026"). Also a "Try the sample" button loading the synthetic demo receipt image and policy.
2. Extraction: on-device OCR (tesseract.js, eng) for images, a text layer for PDFs, and deterministic parsers for store, purchase date, line items and amounts, with a confidence and "check this" flag per field.
3. Policy analysis: deterministic clause segmentation and window/anchor/scope detection. Every evidence span is **verified by code** to be a verbatim substring at its offsets.
4. Per-item deadlines using the date convention in §5.3, a separate clock for each item.
5. An uncertain state: if a governing clause doesn't say when the clock starts, the item is `needs_answer`, and the UI asks **exactly one question per ambiguous clause** (one question card visible at a time).
6. Corrections: editing the store, purchase date, delivery date, an item description, amount or category, or a question answer recomputes every deadline immediately. Changed cards show "was → now", and a correction log is kept.
7. Refusals: no policy → no deadlines at all; a policy without a quotable return window → refusal; an item with no matching clause → "No policy line covers this item"; business-day windows → "not computed" (unsupported, explained); conflicting clauses → "conflict", with both passages shown.
8. Export: an `.ics` file (one all-day event per computed item, with an alarm at 09:00 SGT the day before) and a printable evidence pack (an in-app print view plus a downloadable self-contained `.html`).
9. Privacy: everything runs in the browser. A production CSP blocks network connections other than same-origin. OCR assets are self-hosted. Nothing is uploaded, and no account exists.
10. Persistence (P1, but planned): the case state (not the image) is saved in `localStorage` so that reload keeps the work. "Start over" clears it.

**P1 (do if time, in this order):** PDF without a text layer → render page 1 with pdf.js and OCR it; the persistence above; a mobile layout under 720 px.
**P2 stretch (gated, §9.3):** suggesting item categories with a local small open model. Only after the release candidate is green, after DEV's deadline (19 Oct 15:00 SGT), and with the heavyweight lock.

**Non-goals (explicitly cut):** legal interpretation or advice; judging item condition ("unopened", "tags attached"). The clause text is shown so the user reads the conditions themselves. Also cut: business-day arithmetic and public-holiday calendars; refund amounts or restocking fees; multiple receipts per case or a dashboard of many purchases; accounts, sync, a backend or email/SMS; scraping or fetching store policies from the web (the **user supplies** the policy); languages other than English; currencies other than SGD formatting (amounts are display-only); notifications other than the .ics; hosted LLMs; and real personal receipts in fixtures or the demo.

### 4.3 Persisted JSON schema

`localStorage['returnwindow.v1.case']` = `JSON.stringify(CaseState)`. `persist.ts` holds a zod 4 schema that mirrors §4.1 exactly. It checks `schemaVersion === 1`, CivilDate regex + calendar validity, span invariants against `policy.text`, and `items[].id` uniqueness. If validation fails, the key is removed and the app starts empty with the toast "Saved case couldn't be read and was cleared."

## 5. Domain rules, states, transitions and invariants

### 5.1 Case flow (UI-level state machine, `case-store.ts`)

`empty` → (receipt added) `reading_receipt` → `receipt_ready` | `receipt_failed`
`empty|receipt_ready` → (policy added) `policy_ready`
both present → `workspace` (derived `CaseResult` shown)
`workspace` → (correction/answer) `workspace` (recompute, diff highlighted)
any → (Start over) `empty` (localStorage cleared)
`reading_receipt` → (Cancel) `empty` (worker terminated)

When there is a receipt but no policy, the workspace shows the extracted receipt with the case refusal `no_policy`, and no item gets a date. Missing-policy refusal is a visible state, not a disabled screen.

### 5.2 Policy analysis rules (`policy-parser.ts`)

1. **Normalise:** CRLF/CR → LF only. Offsets refer to this normalised text, and `PolicyDoc.text` stores it.
2. **Segment into clauses.** Split at each LF, and inside a line at sentence ends: `.`, `!`, `?` or `;` followed by whitespace, except after a number with a decimal point or after the abbreviations `e.g.`, `i.e.`, `etc.`, `No.`, `approx.`. Trim leading bullets (`-`, `*`, `•`, `–`, `\d+[.)]`) and whitespace by moving `start`, not by editing the text. Drop empty segments.
3. **Window detection** (case-insensitive) inside a clause that also contains a return keyword (`return`, `returns`, `returned`, `refund`, `exchange`): `(\d{1,3}|<number word>)(?:\s*\(\d{1,3}\))?[\s-]*(calendar\s+|business\s+|working\s+)?(day|days|week|weeks|month|months)\b`. Number words cover one–ten, fourteen, fifteen, twenty, twenty-one, thirty, forty-five, sixty and ninety. "thirty (30) days" yields 30, and if the word and the digits disagree the clause is treated as having no window. Units: no qualifier → `days`, `calendar` → `calendar_days`, `business`/`working` → `business_days`, plus weeks and months. If one clause holds two different windows, it is split into one clause per window when they are separated by a category phrase. Otherwise the clause is a `conflict` source (see the matcher).
4. **Anchor detection** inside the same clause:
   - purchase: `(of|from|after)\s+(the\s+)?(date\s+of\s+)?(purchase|purchasing|sale|transaction|order\s+date|invoice\s+date|receipt\s+date)` and `(from|after)\s+(the\s+day\s+)?you\s+(buy|bought|purchase)`;
   - delivery: `(of|from|after)\s+(the\s+)?(date\s+of\s+)?(delivery|arrival)`, `(from|after)\s+(you\s+)?(receive|received|receiving)\b`, `(of|from|after)\s+receipt\s+of\s+(the|your)\s+(item|items|order|goods|parcel)` and `(once|after)\s+(it|they|your\s+order)\s+(is|are|has|have)\s+(been\s+)?delivered`;
   - if both match, or neither does → `unspecified`. ("Whichever is later" is not supported in the MVP and falls back to unspecified, which is safe.) The anchor span is the matched substring.
5. **Exclusion detection:** `final sale`, `non-returnable`, `not eligible for (a\s+)?return`, `cannot be returned`, `no returns`, `not returnable`. Scope `marked` if the clause contains `marked` or `labelled|labeled` + final sale/clearance, otherwise `categories` if category words are present, otherwise not an exclusion (it's ignored as too vague and listed under "Passages not used").
6. **Scope:** `categoriesInText(clause)` → `categories`; else `all other`, `other items`, `all items`, `everything else`, `most items`, `any item` → `default` with that span; else `default` with span null.
7. Clauses that are neither window nor exclusion are not in `clauses[]`. The UI still shows the whole policy text.
8. **Invariant P1:** every `TextSpan` produced satisfies `verifySpan(policy.text, span)`. `window.span`, `anchor.span` and the scope spans lie inside `clause.span`. The engine asserts P1 before returning, and the UI refuses to render a highlight whose span fails `verifySpan`, showing the error "Evidence mismatch; highlight hidden". The fuzz test (§10) proves this never triggers.

**Category lexicon** (`categories.ts`; priority order electronics > footwear > apparel > beauty > home > groceries; plural/singular insensitive; whole-word):
- electronics: electronics, electronic, earbuds, headphones, earphones, laptop, tablet, phone, smartphone, charger, cable, camera, speaker, smartwatch, console, gadget, gadgets
- footwear: footwear, shoes, shoe, sneakers, sneaker, sandals, boots
- apparel: apparel, clothing, clothes, garment, garments, shirt, t-shirt, tee, dress, jeans, trousers, pants, jacket, scarf, skirt, socks
- beauty: beauty, cosmetics, skincare, makeup, fragrance, perfume, lipstick
- home: home, homeware, homewares, kitchen, mug, cup, plate, bowl, towel, bedding, lamp, cushion
- groceries: groceries, grocery, food, snacks, beverages, perishable, perishables
- anything else → `other` with origin `default`.
`marker.finalSale` = description matches `final sale|clearance|as[- ]is`.

### 5.3 Date convention (shown verbatim in the UI and evidence pack)

> "Dates are calendar dates in Singapore time (Asia/Singapore). The day of purchase or delivery counts as day 0. A 30-day window ends at the end of day 30. 'Days' with no qualifier are treated as calendar days. A one-month window ends on the same date next month, or on the month's last day if that date doesn't exist."

- `deadline = addDays(start, n)` for `days`/`calendar_days`; `addDays(start, 7n)` for weeks; `addMonthsClamped(start, n)` for months.
- `business_days` → `unsupported`, never a date.
- `today = todayInSingapore(now)`; `daysLeft = diffDays(today, deadline)`; urgency: `closed` if < 0, `last_day` if 0, `closing_soon` if 1–3, `open` if ≥ 4.
- No `Date` arithmetic on civil dates anywhere. Only `todayInSingapore` touches `Date`.

### 5.4 Matching precedence (`matcher.ts`)

For each item:
1. `marked` exclusion clause + `item.marker.finalSale` → `exclusion`.
2. `categories` exclusion containing `item.category.value` → `exclusion`.
3. `categories` window clauses containing the category: one → use it; several with identical (amount, unit, anchor) → use the first; several that differ → `conflict`.
4. Otherwise `default` window clauses, with the same rule as 3.
5. Otherwise `none` → `no_policy_match`.

### 5.5 Outcome rules (`engine.ts`) and the one question

- Case refusal: `policy === null` → `no_policy`. A policy with zero window clauses → `no_window_in_policy`. `receipt === null` → `no_receipt`. When refused, every item has no date and `questions = []`.
- Window clause with unit `business_days` → `unsupported`.
- Anchor `purchase` → purchase date needed; if null → `missing_input purchaseDate`.
- Anchor `delivery` → if `deliveryDate.value` is set, compute; else `missing_input deliveryDate` **plus** the question `delivery:${clauseId}` (kind `delivery_date`, prompt "When was your order delivered?").
- Anchor `unspecified` → look at `answers` for `clock:${clauseId}`:
  - none → `needs_answer` and question `clock:${clauseId}`, kind `clock_start`;
  - `purchase` → computed (`via: 'answer'`);
  - `delivery` → needs `deliveryDate`; if set, computed (`via: 'answer'`), else `missing_input deliveryDate` (the delivery date is collected **inside the same question card**, so the user still sees one question);
  - `unsure` → `unsure`, with `earliestPossible` = purchase-anchored deadline (delivery can't be before purchase, so this is the earliest possible last day).
- **Exactly one question per ambiguous clause**, whatever the number of items it governs. Questions are deduplicated by id. The UI shows `questions[0]` and a counter "1 of N" when N > 1.
- Exact clock-start prompt: `"This passage says “{window.span.text}” but not when the clock starts. Does it start on the purchase date ({formatLong(purchaseDate)}) or when the order was delivered?"`. Buttons: **Purchase date** · **Delivery date** (reveals a date input with a confirm button) · **Not sure**.
- **Invariant E1:** `computeCase` is a pure function of `(state, todayInSingapore(now))`.
- **Invariant E2:** an item has a `deadline` iff `status === 'computed'`.
- **Invariant E3:** every `clauseId` referenced exists in `policy.clauses`.
- **Invariant E4:** a deadline is never before its start date, and `diffDays(start, deadline) === n` (or ×7) for day/week units.
- **Invariant E5:** `.ics` events ⇔ `computed` items, one-to-one.

### 5.6 Receipt parsing (`receipt-parser.ts`)

- **Store:** the first line in the top 25% of lines with ≥ 3 letters that is not a date, phone, address keyword (`road|rd|street|st|avenue|ave|#\d|singapore \d{6}`), URL or `receipt|invoice|tax invoice|order`. Its confidence is the line's confidence.
- **Purchase date:** candidates come from every line. Priority goes to lines containing `date|order date|purchased|txn|transaction`; otherwise the first date found. Formats: `DD/MM/YYYY`, `DD-MM-YYYY`, `DD.MM.YYYY`, `DD/MM/YY` (→ 20YY), `YYYY-MM-DD`, `D Mon YYYY`, `D Month YYYY`, `Mon D, YYYY`. A numeric day/month pair is read as **DMY** (Singapore). If both parts are ≤ 12 and differ, set `needsCheck = true` with note "Read as day/month (Singapore format)". Invalid calendar dates (31/02/2026) → not a candidate. Several distinct dates → warning `multiple_dates_found`, the prioritised one is picked and `needsCheck` set. OCR repairs inside date tokens (`O→0`, `o→0`, `I|l→1`, `S→5` only between digits/separators) → `needsCheck`, note "Some characters were guessed".
- **Items:** lines with a trailing amount `(?:S?\$)?\s?(\d{1,5}[.,]\d{2})\s*$`, not matching `subtotal|sub-total|total|gst|tax|vat|change|cash|visa|mastercard|nets|paynow|amex|rounding|discount|balance|tendered|payment`. A quantity prefix is `^(\d{1,2})\s*[x×@]\s+`. Description = the text before the amount, trimmed of SKU-like tokens (`^[A-Z0-9-]{6,}\s+`). The confidence is the mean of the line's word confidences.
- **Total:** a line matching `^\s*total\b` (not subtotal) with an amount. If `sum(items) ≠ total` (± 1 cent) → warning `items_total_mismatch` (shown, not blocking).
- `needsCheck` is also set when confidence < 70.

### 5.7 Corrections (`corrections.ts`)

- Each correction produces a **new** `CaseState` (immutable) with the field's `origin: 'corrected'`, `confidence: 100`, `needsCheck: false`, and appends a `Correction` with `from` = previous display value.
- An item category correction sets `category.origin = 'corrected'`.
- An answer correction replaces the existing answer for that question id; it doesn't append a duplicate.
- Validation errors return `{error}` and leave the state unchanged (`delivery_before_purchase` when the delivery is earlier than the purchase date; also checked when the purchase date is corrected to after an existing delivery date).
- **Invariant C1:** applying correction X, then correcting back to the original value, gives a `CaseResult` deep-equal to the original's items and questions (the log grows, the results don't).
- The UI diff: the store keeps `previousResult`; after a recompute, cards whose outcome changed show "was {old} → now {new}" for 6 s, and stay listed in the "Changes" section of the evidence pack. An `aria-live="polite"` region announces "3 deadlines updated".

- Runtime: reuse the DEV project's already-downloaded llama.cpp b11687 and Gemma GGUF under `$W/cache/dev` **read-only**, started through a new `scripts/llm-suggest.mjs` on port 8091. Only one llama-server may run on the machine at a time.
